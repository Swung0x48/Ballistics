# 计划：作为路线生成器还缺什么

这一页是计划。第 1 条的第一版做了（下面“第一版”一节；格式见 [files.md](files.md) 的“分段的路线文件”），其余都还没做。

## 背景

以后的分工设想是这样：Ballistics 生成路线，Ballrain 那边由一个 RL 执行模型在引擎里按路线闭环去走，走完把结果交回来。两边只交换文件。Ballistics 仍然不启动引擎，也不驱动引擎（[design.md](design.md) 的第 1 条决定）。

清单的来源：Ballrain 那边的会话读了这里的 README、[solver.md](solver.md)、[design.md](design.md) 和最近的提交，写出一份“作为路线生成器还缺什么”，说是项目负责人要把它写成计划（2026-11-21）。下面按那份清单的优先次序排，每条写明三件事：现在有什么（对过代码和文档）、打算怎么做、做到什么程度算完。

末尾原来列了 4 个要项目主人拿主意的问题，他的答复记在最后一节；第 1 条按答复改了，附了版本 2 的草案。

## 现在有什么

- **路线文件**（`ballistics/route.py`，格式见 [files.md](files.md)）是 Ballrain 已经读的参考线格式，版本 1：
  - `points`：沿路线每 0.5 弧长一个球心位置；
  - `sector`：每个点在第几小节；
  - `t_ms`：经过每个点的游戏时间，以毫秒计；
  - `meta`：关卡、起点和盘点的位置、是否完整、留下的断点、吃到的分数球。
- 每关只写一条标准线，走到第一个留下的断点就停。备选路线（`shortcut.alternatives`）只在求解结果和清单里，不进文件。
- 求解结果（每小节一个 pickle）里其实有多得多的东西：
  - 每一段的种类：跟随器走的、细搜跨过的、变球、推栅栏、乘上升边；
  - 每段的起止状态和按键，按物理步记；
  - 每段的球种，以及机关的状态（从物理核的场景读出来，见 [mechanisms.md](mechanisms.md) 的“粗层的状态”）；
  - 细搜出来的每一段，起点扰动后重放 20 次还有几次能到；
  - 纸球经过风扇的每一段，在两档判定下各到不到。

  这些原来都没写出来。第 1 条的第一版把段的种类、球种、变球、推栅栏、乘风扇、推板和跷跷板的状态变化、细搜段的到达次数、纸球的两档写进了 `L<nn>.segments.json`。

## 1. 输出：分段的路线文件（最要紧，也最便宜）

执行模型要的是分段的路线。每段写明：

| 字段 | 从哪里来 | 第一版的做法 |
|---|---|---|
| 段的种类和范围（沿参考线的弧长区间、物理步区间） | 求解结果的段 | 直接写；连着的跟随器段合成一段，在变球、机关、断点、腾空处断开 |
| 要求的球种；在哪里变球、变成什么 | 段的球种和变球段 | 直接写；变球写成一段，带变球器的名字和位置 |
| 走廊宽度 | 还没有 | 粗略的：每段的起点按扰动重放（已有的 20 次）得到的轨迹包络，取每个点离参考线的最大偏差；跟随器段另外加一个“离路面边缘多远”的上限。标成“粗略，不是证明” |
| 出口区域，出口速度和方向的范围 | 还没有 | 粗略的：同一批扰动重放在段末的位置盒子、速度大小和水平方向的区间 |
| 机关标注：哪个物体、做什么 | 段的种类和段前后的机关状态 | 例如“推开栅栏 P_Modul_01_03：石球在此按 −x 键 1.5 游戏秒”“推倒推板：木球或石球，撞上时速度至少多少（取这一段轨迹撞上那一刻的速度，以及扰动重放里最低的那个）”“过跷跷板，石球会把它翻过来” |
| 机关状态或时机的要求 | 粗层状态 | 段开始时各机关应处在的状态（栅栏开没开、推板倒没倒、跷跷板哪头低）。等升降机、秋千这类按时间动的机关接进来，再加时机（相位） |
| 留下的断点 | `meta.left_breaks` 已有 | 断点也写成一段，标“没解出来”，带两边的位置；断点之后从静止接着列的那部分照样写出来，但标“假定从这里静止起步” |
| 多条路线 | `shortcut.alternatives` | 每小节的备选路线写成分支：从标准线的哪一点分出、在哪一点汇回（或到哪个盘点），各带预计时间和容错率 |

- 格式由两边一起定（项目主人的答复）：字段按 Ballrain 执行模型要读的东西来，这里先出草案（下面“版本 2 草案”），交 Ballrain 那边过目。版本 1 的参考线照旧写，两边现有的东西不用动。参考：Ballrain 的 `docs/l2-branches.md`（v2 多分支）里，各段用 `when`（球种加位置盒子或小节）描述，分支有 `phases`。
- 先写这几项：每段的球种、变球点、出口区域和出口速度、方向的范围、机关标注。走廊宽度、机关状态要求、分支排在后面。
- 走廊和出口先用粗略的范围（扰动重放的包络），文件里标明“粗略”，不等证明管子（项目主人的答复：执行模型是闭环的，粗略范围够用）。
- 写法：先在 [files.md](files.md) 里写出格式；再写一个只读求解结果的导出器，和现在的 `route.py` 一样不跑任何推演，只有“粗略走廊和出口”要用已有的扰动重放结果，不够时补跑（都在物理核里）；最后写一个读文件的测试，读回来逐项对上。
- 时间都写游戏时间（毫秒）；按键写成物理步数，并注明 132 步一游戏秒。
- 做到什么算完：第 1 关全部和第 2 关第 1、2、5 小节写出版本 2 文件，每段的字段都有，读回测试过；第 2 关第 3、4 小节写出来的文件里，断点段标得清楚。
- 和 [design.md](design.md) 的“证明管子”的关系：管子是每段的进入和离开范围，正好对应走廊和出口条件。第一版先写粗略的范围，不等独立检查器；以后有了管子，同样的字段换成证明出来的数，文件里标明是哪一种。

### 版本 2 草案（Ballrain 看过一遍，按它的意见改了；还没定）

和版本 1 的 `L<nn>.npz` 放在一起，另写一个 `L<nn>.segments.json`。版本 1 不变，执行模型照旧可以只读它。

```json
{
  "version": 2,
  "level": 2,
  "generator": "ballistics",
  "line": "L02.npz",
  "line_sha256": "...",
  "map_sha256": "...",
  "time": "game ms",
  "ticks_per_game_second": 132,
  "routes": [
    {
      "id": "standard",
      "complete": false,
      "segments": [ ...每段一项，见下... ]
    }
  ]
}
```

- `line_sha256`、`map_sha256`：`L<nn>.npz` 和地图文件的 sha256，用来核对这份文件和线、地图是同一套（Ballrain 读参考线时本来就按 sha256 钉版本）。
- 位置都是世界坐标里的球心 (x, y, z)，游戏单位。

每段：

| 字段 | 含义 |
|---|---|
| `i`、`sector` | 第几段，在第几小节 |
| `s`、`t_ms` | 这一段在参考线上的弧长区间、游戏时间区间（和 `L<nn>.npz` 的 `points`、`t_ms` 对得上）。参考线停在第一个断点，所以断点之后的段不在线上：那里 `s` 和 `t_ms` 为 `null`，另给 `own_s`、`own_t_ms`，是从这一段自己的起点量起的弧长和时间 |
| `kind` | `roll`（跟随器走的）、`crossing`（细搜跨过的）、`flight`（腾空）、`fan_rise`（乘风扇上升）、`operate`（推机关）、`transform`（变球）、`break`（没解出来的断点）。以后接进升降机时用 `elevator` |
| `ball` | 这一段的球种：`wood`、`stone`、`paper` |
| `source` | 这一段从哪来。现在都是 `"kernel"`：物理核里的结果，没在引擎里跑过 |
| `transform` | 只在 `kind` 是 `transform` 的段：`{"at": 变球器名, "pos": [x, y, z], "from": 球种, "to": 球种}` |
| `exit` | 出口：`{"box": {"min": [x, y, z], "max": [x, y, z]}, "speed_h": [低, 高], "vy": [低, 高], "dir": [dx, dy, dz], "dir_tol_deg": 15, "rough": true, "from": "20 nudged reruns"}`。`box` 是段末位置的盒子；`speed_h` 是水平速度的区间；`vy` 是竖直速度的区间，只在腾空段和出口有落差的段写；`dir` 是世界坐标里的单位向量，一般段只取水平（dy 为 0），腾空段写三维；`dir_tol_deg` 是容差角。都取段末在扰动重放里的范围；`rough` 为真表示是粗略的包络，不是证明出来的 |
| `corridor` | 走廊：沿这一段每隔一段弧长给一个半宽，取各次扰动重放到参考线的最大横向距离，`{"every": 1.0, "half_width": [...], "rough": true}`。和 `exit` 出自同一批重放 |
| `mechanisms` | 这一段对机关做的事，每项 `{"name", "type", "does", "ball", ...}`，`name` 用地图里物体的原名。例如推板 `{"name": "P_Modul_25_01", "type": "push_board", "does": "push_over", "ball": ["wood", "stone"], "impact_speed": [低, 高]}`；栅栏 `{"name": "P_Modul_01_03", "does": "push_open", "key": "-x", "hold_ms": 1500}`；跷跷板 `{"name": "P_Modul_30_01", "does": "cross", "tips": true}`。按键和按住时长只是提示，执行模型不照着回放 |
| `arrives` | 扰动重放 20 次里还到的次数（细搜段才有） |
| `break` | 只在 `kind` 是 `break` 的段：两边的位置。它之后的段标 `"assumed_rest_start": true`，意思是假定球在断点那边静止起步，**不能当作可行** |

- 先写：`kind`、`ball`、`source`、`transform`、`exit`、`corridor`、`mechanisms`、`break`。`corridor` 按 Ballrain 的意见提前了：跟踪器判断偏离了没有主要靠它。
- 排在后面的：段开始时机关应处的状态 `states`、分支 `routes[1:]`（从哪一点分出、在哪一点汇回）、SR 和 HS 的数（见第 4 条）。
- Ballrain 那边训练暂停中，还没决定实现读取端；这份草案只是格式过了一遍。

### 第一版（做了）

`python -m ballistics route ... --mesh <网格>` 在 `L<nn>.npz` 旁边写出 `L<nn>.segments.json`（`ballistics/segments.py`，格式和逐项的含义见 [files.md](files.md)）。照草案“先写”的那几项都有：`kind`、`ball`、`source`、`transform`、`exit`、`corridor`、`mechanisms`、`break`，以及 `s`/`t_ms`（线外的段是 `own_s`/`own_t_ms`）和 `assumed_rest_start`。和草案不同的地方列在 files.md 那一节末尾，要再交 Ballrain 那边过目。

- 出口和走廊怎么来的：细搜段和腾空段整段扰动重放 20 次；跟随器走的段按每游戏秒一窗，每窗从路线在窗口开始时的状态扰动起重放 20 次。跟随器的按键是闭环选的，整段开环重放几秒内就掉（第 1 关一段 30 游戏秒的，20 次全掉）；改用跟随器本身沿这段轨迹重跑，6 次里只有 1 次走到头，一次要 20 秒，也不行。所以跟随器段的包络说的是“开头还在路线上，一游戏秒里会偏多远”。
- 推板的撞击速度：撞上的那一步推板才醒，球在这一步里失去大部分速度，转角下一步才变，所以按醒来那一步之前的球速算。
- 还没有的：`states`（段开始时机关应处的状态）、分支、SR 和 HS 的数。木球、纸球从跷跷板上过去而没翻它，现在不标。
- 读回测试：`tests/test_segments.py`，做出来的地面和 test_props 里的推板、栅栏、跷跷板。

## 3. 为机关特意规划

清单里说粗层不知道“后面的机关要石球，所以先去变石球”，也排不出“先推倒、再从上面过去”。这一条正在做，交审查的这一版已经有：

- 粗层的状态是球种加每个机关的简单状态。规划会为了推栅栏先去变石球，会先推倒推板再过去，也会翻跷跷板（[mechanisms.md](mechanisms.md) 的“粗层的状态”）。

还缺：

- 落石（P_Modul_34）不在状态里，“先在下层推开、再从上层过”还排不出来。
- 按时间动的机关没有相位状态。
- 粗层能排出来的长计划，跟随器和细搜不一定走得出来，第 2 关第 3 小节卡在上升边就是这样。
- 跟随器的断点每次都算新的一处，同一处反复跨不过去时不会停下（mechanisms.md 里记着这个缺口）。

做到什么算完：第 2 关第 3 小节按标准走法实际解通，路线文件里各段的机关标注和状态要求都对。

## 4. 路线不够多样，也不够好

| 缺的 | 打算 |
|---|---|
| 备选路线只有“经过孤岛”一种来源 | 加别的来源：钢轨中途离开；借箱子或道具球反弹和转向；从高处直接飞到标准路线后面才到的地方（[design.md](design.md) 里列着） |
| 各小节的备选路线没有接成整关的路线 | 每小节的备选路线带出口状态，下一小节从各个出口状态各解一遍，再按整关排；数量会成倍增加，要限制每小节带几条往下走 |
| 只算 SR，不算 HS | 分数球已经记着吃到哪些（`extras`）。HS 沿用 Ballrain 的口径（项目主人的答复）：分数加上生命数乘以生命奖励（通关结算每个 200 分），时间按游戏里分数随时间的衰减折成分数（每秒减 2 分，扣到 0 为止，暂停时不扣，[game/rules.md](game/rules.md)）；通关时还跟着的分数小球每个加 20，过盘点时会丢掉。这些和 Ballrain 的口径核对过一致（Ballrain 那边说的）。SR 和 HS 分开排序，不折成一个数 |
| 搜到的是“一个”走法，不是最快的 | 细搜找到以后接着以时间为目标优化一段时间；跟随器看得更远（现在只看一个游戏秒）；起飞边加“带着速度起跳”的 |

作为可行性候选，现在这样可以交出去；用来挑最优还不够。这些都排在第 1 到第 3 条之后。

## 5. 反馈通道

还是只交换文件：Ballrain 的执行模型试走以后写一份结果文件，Ballistics 读进来，再重新规划。

- **结果文件里要有**：
  - 路线文件和版本（哪一份、哪一条分支）；
  - 每段的尝试次数和成功次数；
  - 失败时进入这一段的状态（位置、速度、角速度、球种，各机关的状态）；
  - 能重放的按键凭证：起始状态加按键序列，按物理步记，注明帧率；
  - 它是在引擎的哪种运行方式下得到的。
- **Ballistics 怎么用**：
  - 成功率低的段：粗层上代价加大，或者拿掉那条边，和现在“走不通的边从粗层拿掉”一样；
  - 失败时的入口状态：作为细搜的新起点，找一段在那些状态下也能走的走法；
  - 按键凭证：只拿来对照物理核（重放比对），不当成规则的依据，除非按 [physics.md](physics.md) 的做法正式标定。
- 做到什么算完：两边约定好格式写进 [files.md](files.md)；有一个读结果文件、调整代价、再写出路线文件的来回，用一份手写的结果文件测试过。

## 项目主人的答复

原来列的 4 个问题，项目主人的答复（经 Ballrain 那边的会话转来，2026-11-21）。这只是答复，不代表这份计划已经批准，计划的审查和提交仍由他定。

1. **格式**：两边一起定，不由这边单方面定；字段按 Ballrain 执行模型要读的东西来。先写每段的球种、变球点、出口区域和出口速度、方向的范围、机关标注。草案写在这份计划里（第 1 条的“版本 2 草案”），交 Ballrain 那边过目。

3. **次序**：先做第 1 条（输出格式），再去走通第 2 关第 3 小节（第 2、3 条）。
4. **HS 的打分**：沿用 Ballrain 的口径，分数加生命数乘以生命奖励，时间损失按游戏里分数随时间的衰减折成分数。SR 和 HS 分开排序，不硬折成一个数。
